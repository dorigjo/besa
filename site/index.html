Besa

Exact-action authorization before consequential AI-agent execution.

After identity and before the side effect, Besa binds the principal, agent, authority, operation, resource, constraints, expiry, and nonce. It issues a signed allow or deny capability, then links the result to signed evidence.

  ↓  replay-enforced execution

The problem

Authentication says who connected. Tool permissions say what may be called. Neither proves whether this exact payment, deployment, message, or database mutation was authorized under these exact constraints, nor links the outcome to that decision.

The category

Approve. Enforce. Prove.

Besa sits after identity and before the side effect. It evaluates exact action envelopes, verifies narrowed delegation, fails closed on mismatch or replay, and signs capabilities plus post-action evidence.

What Besa proves
  • Which declared principal, agent, and authority the signed capability binds
  • The exact tool, operation, resource, scopes, constraints, expiry, and nonce admitted
  • Whether policy and every narrowed delegation link authorized that exact action
  • Whether enforced replay protection accepted the action nonce only once
  • Which signed result evidence links the action, capability, and execution outcome
CLI + Self-hosted Verifier 
npm install @dorigjo/besa

npx besa --help

besa serve --port 8787 --action-trust verifier-trust.json

# Admission mode also requires BESA_ADMISSION_TOKEN
besa serve --port 8787 --trust issuer-trust.json \
  --key-file .besa/key.json \
  --action-policy examples/action-policy.yaml

Status

v1.1.0. Local library, MCP middleware, and a production-oriented self-hosted HTTP verifier with health/readiness probes, request limits, rate limiting, token-protected admission, keyless verification mode, Docker deployment, tests, and conformance vectors. Besa does not operate an official public verifier instance. No independent third-party security audit has been performed yet.
