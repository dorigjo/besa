## Thread

**1/** Giving an AI agent valid credentials does not mean every action it can
technically perform should execute.

Identity answers WHO.

Besa asks: MAY THIS EXACT ACTION execute on THIS resource, under THESE
constraints, before THIS expiry?

**2/** Concrete case:

```text
AWS credentials: accepted
contract: DEPLOY staging
request: DELETE production-db

DENY ACTION_NOT_GRANTED
executor called: no
```

That is the boundary Besa owns.

**3/** The protocol separates three artifacts:

- Action Envelope: the canonical proposed action
- Action Capability: signed exact allow/deny
- Action Evidence: signed link to the supplied result

Optional delegation narrows authority. Replay state is consumed before execution.

**4/** Besa sits after IAM/OAuth/MCP Auth and immediately before the
consequence-bearing handler.

It does not replace identity, cloud policy, MCP routing, a payment rail,
observability, or a sandbox.

**5/** Try the real Ed25519 deny/allow path locally:

```bash
npm install @dorigjo/besa
npx besa demo
```

No account and no hosted Besa service.

**6/** v1.1 includes a TypeScript SDK/CLI, `withBesa` and `withBesaMcp`, frozen
conformance vectors, replay and evidence interfaces, and a self-hosted HTTP
verifier.

No independent third-party security audit has been completed.

**7/** Source, spec, threat model, benchmarks, and demo:

https://github.com/dorigjo/besa

I am looking for technical criticism of the trust boundaries and whether a
provider-neutral exact-action contract is useful in real agent systems.
